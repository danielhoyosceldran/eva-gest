# Code review — October 2026

A read-only review of the whole app on 2026-10-05: data integrity, money, appointments,
backup and restore, logging, WPF/MVVM, security and deployment. This page records what
it found, what the owner decided for each finding, and the commit that fixed it.
The same bugs have rows in [`bugs.csv`](../bugs.csv).

Overall verdict: **usable and well built** — money, VAT, audit trail and the restore
path were already careful. The findings were about surviving a bad day (a failed
update, a damaged backup, a restore) rather than about everyday correctness.

## Accepted as they are

The owner reviewed these and decided no change is needed. They are recorded so a later
review does not raise them again as if they were new.

| ID | Finding | Decision |
|---|---|---|
| B-1 | Backups are kept only in `%LOCALAPPDATA%\EvaGest\Backups`, on the same disk as the database, so a disk failure, theft or ransomware loses both. | **Accepted.** Already taken into account by the owner and fine as it is; no second backup location is added to the app. |
| S-1 | The database and its backups hold client names, phones and emails unencrypted. | **Accepted.** Encryption at rest is not considered necessary for this shop. |
| U-1 | The "last backup" date in Settings is formatted with a fixed `dd/MM/yyyy HH:mm` instead of `AppLanguage.Culture`. | **Accepted.** Both interface languages use that same format; not worth changing. |

### Behaviour that now differs from the spec's wording

- **CU-01b (`plan/casos-us.md` §3).** The rule is unchanged: an overlap never blocks,
  and the appointment *can be saved anyway*. What is new is that saving into a full
  slot asks first, instead of relying on the red line alone. An edit that leaves the
  date, time, duration and worker as they were does not ask again.
  Note that a shop where no worker has a weekly schedule has no capacity in any slot,
  so every booking without a worker would ask. Workers' schedules have to be filled
  in for the question to mean anything.
- **CU-09b (restore).** After a restore the app closes itself instead of asking the
  user to reopen it.
- **CU-12 (startup).** A copy of the database is taken before pending migrations run,
  and the app refuses to migrate if that copy cannot be written.

## Tests

Regression tests were written by a separate tester pass from each problem's
description, not from the fix, and each problem test was shown to fail on the commit
before its fix (`b532cf4`, plus one in `bd273c2`). Where the fix introduced the only
testable seam (B-2, B-4), the tests were checked by breaking the fix deliberately
instead.

**G-1 has no automated test**: it needs two real EvaGest processes. Manual check:

1. Start EvaGest and minimise it, then launch it again: the window comes back to the
   front and Task Manager shows a single `EvaGest.exe`.
2. Cover EvaGest with another window (not minimised) and launch it again: EvaGest comes
   to the front.
3. Launch it twice in quick succession: the second shows *EvaGest ja està obert* and
   exits.

## Left open

- A failed **automatic** backup is only logged at startup; the user is not told
  (row in `bugs.csv`, not solved). With B-3 in place, a damaged live database makes
  every daily copy fail, so this matters more than it did.
- Editing an appointment's details (time, worker, notes) and charging it still write no
  appointment audit row; only status changes and deletions do.
- Changing an appointment to the status it already has writes an audit row whose
  before and after are identical.
- `AppointmentService.Update` lists the editable fields by hand: a new field on
  `Appointment` has to be added there, or edits will silently drop it.
